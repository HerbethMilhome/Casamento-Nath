Armazenamento de RSVP e recados

Registro do que foi implementado no site-de-casamento — escrito para que o trabalho possa ser refeito do zero sem redescobrir as decisões. Estado dos arquivos em 22/09/2026.

Resumo em uma frase: as confirmações de presença e os recados deixaram de viver no localStorage e passaram a ser gravados numa planilha do Google, através de um Apps Script publicado como Web App — com uma etapa de confirmação que impede o site de dizer “confirmado!” para um convidado cujo envio nunca chegou.

1. Escopo — o que estava e o que não estava em jogo

O site veio pronto de terceiros. A tarefa era apenas resolver o armazenamento das confirmações de presença (RSVP) e dos recados, porque um convidado confirma no celular dele e os noivos precisam ver isso em outro aparelho. localStorage não atravessa dispositivos.

Ficou deliberadamente fora do escopo, e continua em localStorage de propósito:

  • Lista de presentes, galeria de fotos, linha do tempo, padrinhos, informações úteis, FAQ.
  • Todo o painel administrativo (src/components/admin/), incluindo os 10 erros de tipo pré-existentes que ele carrega.
  • A autenticação, que é cosmética por design (senha fixa no código, '123456' como bypass do portão de convidados). É uma demonstração, não controle de acesso.

Alternativas consideradas e por que foram descartadas

OpçãoPor que não
Supabase / FirebaseExigem conta, projeto, chaves e manutenção de um backend para gravar duas tabelas. Custo e cerimônia desproporcionais ao problema.
Backend próprio (Express)Precisaria de hospedagem permanente. O express, dotenv e @google/genai no package.json são resquícios desse plano e continuam sem uso — mantidos por escolha.
Google FormsTira o convidado do site e não devolve os recados para o mural.
Google Sheets + Apps ScriptEscolhido. Gratuito, sem servidor, e a planilha já é a interface natural para os noivos: eles leem, filtram e moderam ali mesmo.

2. O problema técnico central

Esta é a parte que mais custa a redescobrir, e a razão de o código parecer estranho. O Apps Script é hostil a chamadas vindas de um navegador.

  1. A URL /exec não responde direto: devolve um redirecionamento para script.googleusercontent.com, e essa etapa intermediária não carrega cabeçalhos de CORS. Resultado: um fetch comum é rejeitado pelo navegador mesmo quando a gravação deu certo na planilha.
  2. Um POST com Content-Type: application/json dispara uma requisição de preflight (OPTIONS), que o Apps Script não sabe responder.

As duas saídas adotadas — ambas intencionais, não são gambiarra a ser “limpa”:

OperaçãoTécnicaPor quê
Escrita
(RSVP, recado)		 fetch com mode:'no-cors' e Content-Type: text/plain;charset=utf-8 text/plain torna a requisição “simples”: o navegador manda direto, sem preflight. Em troca, a resposta vem opaca e ilegível.
Leitura
(recados, confirmação)		 JSONP — uma tag <script> injetada no <head> Tag de script não está sujeita a CORS. O script devolve nomeDaFuncao({...}); e a função existe no escopo global.
A consequência que virou a peça mais importante do sistema. Como a resposta do POST é ilegível, o site não sabe se a gravação funcionou. Por isso cada envio carrega um token aleatório; o Apps Script só registra esse token no CacheService (10 minutos) depois de gravar a linha; e o site então pergunta por JSONP ?confirmar=<token> até obter resposta. Essa ida e volta é a única coisa entre uma falha silenciosa e um convidado indo embora achando que confirmou presença. Se refizer, não corte isso.

5. apps-script/Codigo.gs — o backend

Rotas (todas na mesma URL do Web App)

RequisiçãoEfeito
POST { tipo:'rsvp', … }Acrescenta uma linha na aba Confirmados.
POST { tipo:'recado', … }Acrescenta uma linha na aba Recados, com Aprovado falso.
GET ?confirmar=<token>{ ok, versao, gravado: true|false }
GET sem parâmetros{ ok, versao, recados: [...] } — só os aprovados, mais recentes primeiro.

Todo GET aceita &callback=<fn> e responde em JSONP.

Abas e colunas (criadas sozinhas no primeiro envio)

Confirmados: Data/Hora · Nome · E-mail · Telefone · Vai comparecer · Total de pessoas · Acompanhantes · Restrição alimentar · Detalhe da restrição · Mensagem aos noivos · Situação

Recados: Data/Hora · Nome · Recado · Aprovado (caixa de seleção, criada por setDataValidation a cada linha nova)

Decisões embutidas no script

Nada é sobrescrito — histórico por e-mail. Cada envio é uma linha nova marcada Atual; as respostas anteriores do mesmo e-mail passam a Substituída. Para contar convidados, filtra-se a coluna Situação por Atual. Quem responde sem e-mail fica sempre como Atual — agrupar por nome arriscaria juntar dois homônimos.

O token só é registrado depois da gravação. É o que dá sentido à confirmação:

if (resultado.ok) registrarToken(corpo.token);

function registrarToken(token) {
  if (!token) return;
  CacheService.getScriptCache().put('envio:' + token, '1', 600);
}

O nome do callback JSONP é validado. Ele vem da URL e entra no corpo da resposta — sem essa checagem, qualquer um injetaria código na página que consome o endpoint:

if (!/^[A-Za-z_$][A-Za-z0-9_$]{0,63}$/.test(callback)) {
  return json({ok: false, erro: 'Nome de callback inválido.'});
}

Trava de escrita. LockService.getScriptLock().waitLock(20000) em volta de cada appendRow, para dois convidados enviando ao mesmo tempo não colidirem.

Migração de cabeçalho sem apagar nada. obterAba() reescreve o cabeçalho quando a aba existente tem menos colunas que o esperado — foi assim que a coluna Situação entrou numa planilha já em uso.

Marcador de versão. var VERSAO = '5-jsonp'; aparece em toda resposta GET. É o jeito rápido de saber qual código está realmente no ar.

6. src/services/sheetsApi.ts — o cliente

A escrita, com os dois truques na mesma função:

async function enviar(corpo) {
  const token = gerarToken();

  await fetch(exigirEndpoint(), {
    method: 'POST',
    mode: 'no-cors',
    headers: {'Content-Type': 'text/plain;charset=utf-8'},
    body: JSON.stringify({...corpo, token}),
  });

  await confirmarGravacao(token);   // o que torna o envio verificável
}

A confirmação insiste dentro de um orçamento fixo, porque gravação e consulta são requisições independentes — a segunda pode chegar antes de a primeira terminar:

const esperas = [700, 1200, 1800, 2500];
for (const espera of esperas) {
  await esperar(espera);
  try {
    const resposta = await jsonp({confirmar: token});
    if (resposta.gravado) return;
  } catch { /* rede instável: segue tentando */ }
}
throw new Error('Não foi possível confirmar a gravação na planilha.');

Dois detalhes que parecem supérfluos e não são

O cache-buster _ em toda URL JSONP. Sem ele o navegador guarda a resposta da tag de script e o mural serve recados velhos por minutos depois de uma aprovação.

const query = new URLSearchParams({
  ...parametros, callback: nome, _: Date.now().toString(36),
});

buscarRecadosAprovados devolve null em caso de falha — [] significa “a planilha respondeu e não há recado aprovado”. Quem chama não pode apagar o mural em null, ou uma falha de rede esvazia a tela de quem já estava lendo.

Modo offline. sheetsConfigurado() é falso quando VITE_SHEETS_ENDPOINT não está definido (o normal em desenvolvimento local). Aí tudo volta a cair no localStorage e o app roda sem a planilha.

7. Integração no site

WeddingContext.tsx

(a) submitRsvp virou async e devolve {success, message}. A planilha é a fonte da verdade: se a gravação falha, devolve success:false com mensagem em português e o site nunca mostra a tela de agradecimento.

(b) addGuestbookMessage virou async e deixa o erro subir — quem chamou precisa saber que o recado não foi salvo.

(c) useEffect novo popula o mural. Carrega na montagem e de novo em visibilitychange, porque os noivos aprovam na planilha e voltam para a aba do site esperando ver o resultado:

const carregar = async () => {
  const recados = await buscarRecadosAprovados();
  if (cancelado || recados === null) return;   // null = falha, mantém o mural
  setMessages(recados.map(r => ({ id: r.id, name: r.nome,
    message: r.recado, date: r.data, isApproved: true })));
};

Componentes públicos

Ambos ganharam enviando (trava o botão contra envio duplo) e erro (mensagem visível em português). O trecho que define tudo, em RsvpSection.tsx:

// Só mostramos a tela de agradecimento se a planilha confirmou a gravação.

8. O ajuste paralelo: @types/react

Não fazia parte do pedido, mas impedia qualquer verificação confiável. O package.json nunca declarou @types/react nem @types/react-dom. Sem eles, toda API do React resolvia para any — inclusive o retorno de useWedding() — e o npm run lint (que é tsc --noEmit, não um linter) passava sem checar praticamente nada.

Instalados na versão ^19.3.0. Isso revelou 10 erros de tipo reais e pré-existentes em src/components/admin/ (hasPlusOne ausente, order passado onde é Omittido, heroPhotoUrl e coverPhrase fora de WeddingData) — conhecidos, alheios a esta mudança e fora do escopo.

Sinal de alerta: se o tsc voltar a passar rápido demais ou aceitar algo claramente errado, a primeira coisa a conferir é se @types/react continua instalado. Um npm install a partir de um package.json antigo remove os dois de novo.

9. Para refazer do zero — passos

  1. Criar planilha em sheets.new. Não criar abas nem colunas — o script cria.
  2. Extensões → Apps Script, apagar o conteúdo de Código.gs e colar apps-script/Codigo.gs.
  3. Implantar → Nova implantação → App da Web, com Executar como: Eu e Quem pode acessar: Qualquer pessoa. Autorizar (o aviso de “app não verificado” é esperado — o app é seu).
  4. Copiar a URL terminada em /exec para VITE_SHEETS_ENDPOINT no .env.local. Reiniciar o npm run dev — o Vite só lê variáveis de ambiente na inicialização.
  5. Ao publicar (Vercel, Netlify, Cloud Run…), cadastrar a mesma variável no painel de ambiente do serviço.
  6. Testar: enviar um RSVP (a aba Confirmados deve aparecer) e um recado (aba Recados, com Aprovado desmarcado).

“Qualquer pessoa” é seguro aqui: o script só sabe acrescentar uma linha e devolver recados já aprovados. Ninguém lê a lista de convidados, e-mails ou telefones por ele; a planilha continua privada na conta Google.

10. Invariantes — quebrar qualquer um destes reintroduz um bug conhecido

  • O POST continua mode:'no-cors' com text/plain. Trocar por application/json dispara preflight e nada é gravado.
  • A leitura continua por JSONP. Trocar por fetch quebra no redirecionamento sem CORS.
  • A confirmação por token permanece. Sem ela, falha de gravação vira convidado achando que confirmou.
  • O token só é registrado depois do appendRow, nunca antes.
  • Toda URL JSONP leva o cache-buster _.
  • null de buscarRecadosAprovados nunca esvazia o mural; [] pode.
  • Nenhuma tela de sucesso aparece sem checar result.success.
  • Recado novo entra não aprovado. A moderação é a caixinha na planilha, não o painel admin.
  • O nome do callback JSONP continua validado por regex no Codigo.gs.
  • Se mudar a forma de uma entidade persistida, bumpar o sufixo da chave em STORAGE_KEYS (casamento_guests_v1…) — senão usuários antigos hidratam JSON velho na forma nova e o app quebra.

11. Armadilhas ao mexer depois

Editar o Codigo.gs não muda nada até republicar. O caminho é Implantar → Gerenciar implantações → (ícone de lápis) → Versão: Nova versão → Implantar; a URL continua a mesma. “Nova implantação” cria outra URL e deixa silenciosamente o código antigo servindo — é o erro clássico. Para conferir o que está no ar, abra a URL /exec no navegador: a resposta traz "versao":"5-jsonp".

Sobre o repositório: ele não está sob controle de versão — não há Git, então edições são irreversíveis; confirme antes de apagar ou reescrever arquivos inteiros. Também não há suíte de testes nem runner instalado: a verificação disponível é npm run lint (tsc --noEmit) somada a rodar o app.
